# Sidepad — Windows → 기기 Wi-Fi 확장 모니터

같은 공유기 네트워크에서 Windows의 보조 디스플레이를 기기 브라우저로 전송하는 개발용 앱입니다. Windows는 Electron, 화면 전송은 WebRTC, 기기는 웹 뷰어를 사용합니다. 외부 중계 서버나 계정은 필요하지 않습니다.

**기기 전용 작업 공간을 만들려면 Windows에 가상 모니터가 있어야 합니다.** 이 프로젝트는 [Virtual Display Driver](https://github.com/VirtualDrivers/Virtual-Display-Driver)에 연결합니다. 설치 EXE에는 서명된 드라이버를 포함하며, 바이너리는 빌드 때 내려받고 Git에는 올리지 않습니다. 이미 연결된 물리 보조 모니터도 전송할 수 있지만, 이때 기기는 그 보조 모니터와 같은 내용을 표시합니다.

## Windows 설치 EXE

`Sidepad-Setup-0.2.0-x64.exe` 하나로 앱 설치 → 관리자 확인 → 가상 드라이버 등록 → **1920 × 1080 / 60 Hz 확장 설정**을 진행합니다. 대상은 Windows 10/11의 Intel/AMD x64 PC입니다. Electron 실행 환경과 서명된 드라이버가 포함되어 Node.js, WinGet 및 설치 중 별도 다운로드가 필요하지 않습니다. 재부팅이 필요한 경우 완료로 표시하지 않고, 재시작 후 앱을 열면 남은 화면 설정을 이어갑니다. 자세한 사용법은 [설치 안내](docs/INSTALL.ko.txt)를 참고하세요.

앱은 현재 사용자에게 설치되며 사용자 데이터는 `%APPDATA%\Sidepad`에 저장됩니다. 드라이버 등록과 Sidepad 실행 파일의 **개인 네트워크·로컬 서브넷** 방화벽 규칙에만 관리자 권한을 사용합니다. 앱 자체는 일반 권한으로 실행합니다. Windows 네트워크 프로필·인증서 저장소·드라이버 보안 정책은 바꾸지 않습니다. 앱 제거 시 그 설치 경로의 네트워크 규칙을 정리하며, 공유 가상 드라이버와 사용자 데이터는 남깁니다.

현재 설치 EXE와 앱은 **배포자 코드서명 전**입니다. 포함된 드라이버의 원래 서명은 유효하지만, 앱 다운로드/실행 시 Windows의 게시자 확인 또는 SmartScreen 경고가 표시될 수 있습니다. 정식 코드서명 인증서는 별도 배포 준비 항목입니다.

빌드: Windows에서 `npm ci` 후 `npm.cmd run dist:win`. 결과는 `dist/Sidepad-Setup-0.2.0-x64.exe`, 같은 이름의 `.sha256`, `Sidepad-설치안내.txt`입니다. 빌드에는 인터넷이 필요하며, 공식 드라이버 ZIP의 고정 SHA-256과 카탈로그 서명을 검증합니다. 드라이버 INF/DLL/CAT/XML 및 MIT 고지만 포함하고 DevCon이나 Virtual Driver Control은 배포하지 않습니다. 등록은 Windows SetupAPI/newdev를 호출하는 전용 보조 코드가 처리합니다.

## 버전 배포

`package.json`과 `package-lock.json`의 버전을 맞춘 뒤 해당 커밋에 `v<버전>` 태그를 붙여 GitHub에 push합니다. 예를 들어 앱 버전이 `0.2.0`이면 태그 이름은 `v0.2.0`입니다.

GitHub Actions가 Windows에서 테스트와 빌드를 실행하고 성공하면 설치 EXE, SHA-256 파일, 한국어 설치 안내를 [릴리스 초안](https://github.com/yjjyjjyjjyjj/sidepad/releases)에 첨부합니다. 저장소에 쓰기 권한이 있는 계정으로 초안의 EXE를 받아 설치와 기기 연결을 확인한 뒤 **Edit → Publish release**를 누르면 공개됩니다. 첫 배포인 `v0.2.0`과 버전에 `-beta.1` 같은 사전 출시 표기가 있는 빌드는 초안에서 **Pre-release**가 선택됩니다.

이미 올린 태그의 빌드를 수동으로 시작하려면 **Actions → Windows release draft → Run workflow**에서 브랜치 `main`과 기존 태그명을 선택합니다.

## 소스에서 실행

필요 환경: Windows 10/11, Node.js 22.12 이상, WebRTC를 지원하는 기기 브라우저. 실제 검증한 개발 환경은 Node.js 22.18 및 Windows x64입니다. 특정 모든 기기·브라우저 조합에 대한 실기기 호환성을 보장하지 않습니다.

```powershell
cd E:\DEV\remoteControl
npm.cmd install
npm.cmd start
```

이 작업 폴더에는 의존성이 설치되어 있습니다. 처음부터 설치하는 다른 PC에서는 최초 실행 시 Electron 실행 파일 다운로드도 필요합니다.

### 실행 중인 앱을 유지하며 새 버전 시험하기

기본 실행은 `npm.cmd start`이며 창 제목은 **Sidepad**, 연결 포트는 3210입니다. 창·앱·웹 뷰어에 같은 아이콘을 사용하며, 화면 상단에 개발용 PREVIEW 배지를 표시하지 않습니다. 아이콘 원본은 `src/assets/sidepad.svg`, Windows ICO 및 PNG 재생성 명령은 `npm.cmd run icons`입니다.

개발 중 별도 인스턴스가 필요하면 `npm.cmd run preview`를 사용합니다. 기존 앱은 3210에서 계속 실행되고, 시험 인스턴스는 3212와 별도 사용자 프로필·연결 토큰을 사용합니다. 연결할 기기에서 **해당 창의 새 QR 코드**를 사용합니다. 창 제목은 모두 Sidepad이며, 연결 주소의 포트로 구분할 수 있습니다.

`npm.cmd run preview:hardware`는 포트 3213과 별도 프로필을 사용합니다. 진단 결과를 로컬 `.runtime/hardware-preview-diagnostics.json`에 기록하여 실기기의 코덱 협상 결과를 확인할 수 있게 합니다. 연결 토큰·IP·전체 SDP·화면 영상은 기록하지 않으며, 이 파일은 Git에서 제외됩니다.

`npm.cmd run preview:buffer`는 개발 검증용 포트 3214와 별도 프로필을 사용하며 진단을 `.runtime/buffer-preview-diagnostics.json`에 기록합니다. 비교를 위해 선명하게 / 60 fps로 시작합니다. 이 명령은 일반 사용에 필요하지 않으며, 하드웨어 코덱 선택과 혼잡 조절 기능은 기본 실행에도 포함됩니다.

### 하드웨어 인코딩 선택

기본 **하드웨어 우선**은 송신·수신 양쪽의 `setCodecPreferences()`를 사용합니다. 실제 브라우저가 지원한다고 광고한 H.264 High/Main/Baseline을 먼저 고려하고, 그 공통 규격이 없으면 지원되는 HEVC(H.265)를 Constrained Baseline보다 우선합니다. 해상도와 프레임 설정은 바꾸지 않습니다. **호환성 우선**을 선택하면 기존처럼 H.264를 먼저 고려합니다.

Windows Chromium의 Media Foundation 인코더는 NVIDIA에서 H.264 **Constrained Baseline**을 제외하는 제한이 있습니다. 이 규격만 우선 협상하면 GPU 가속이 활성화된 PC에서도 OpenH264로 전환될 수 있습니다. H.264를 모두 같은 우선순위로 취급하던 기존 코드를 프로파일별 우선순위로 바꾸고, 수신 측도 동일한 선호도를 적용했습니다. [Chromium 공식 구현](https://chromium.googlesource.com/chromium/src/+/main/media/gpu/windows/media_foundation_video_encode_accelerator_win.cc)

이 기능은 지원되지 않는 프로파일을 SDP에 추가하거나 NVIDIA 드라이버 제한을 해제하지 않습니다. 공통 하드웨어 규격이 없거나 인코더 초기화가 실패하면 호환 가능한 소프트웨어 경로로 연결할 수 있으며, 실제 상태를 표시합니다. **NVIDIA 하드웨어 인코딩 확인**은 `getStats()`의 실제 인코더 이름에 NVIDIA가 보고된 경우에만 표시합니다. 가속 기능의 `enabled` 값만으로 성공을 표시하지 않습니다.

진단 보고서의 `sender.codecParameters`는 선택된 프로파일·패킷화 규격이며, `codecNegotiation`은 송수신 지원 코덱, 선호도 적용 결과, 응답에서 협상한 코덱만 담습니다. 전체 SDP는 포함하지 않습니다.

### 저지연 모드

- 화질·프레임 선택과 저지연 설정을 분리했습니다. 저지연 모드를 켜거나 꺼도 선택한 해상도와 프레임을 바꾸지 않습니다. 기본값은 균형 화질, 목표 60 fps이며, 현재 1920 × 1080 가상 화면을 축소하지 않고 캡처합니다.
- 두 모드 모두 글자 선명도와 해상도 유지를 우선하도록 요청합니다. 네트워크나 인코더가 부족하면 프레임이 줄어들 수 있습니다. 저지연 모드에서는 PC 미리보기 재생을 생략합니다.
- 화질별 전송률 상한은 30 fps에서 가볍게 3 / 균형 8 / 선명하게 16 Mbps, 60 fps에서 각각 4.5 / 12 / 24 Mbps입니다. 상한은 고정 전송률이나 실제 프레임 보장이 아닙니다.
- 수신 브라우저가 지원하면 `jitterBufferTarget = 0`을 요청하고, 이전 API인 `playoutDelayHint`만 제공하면 그 API를 사용합니다. 존재하지 않는 속성을 만들어 성공으로 표시하지 않습니다. 이는 버퍼 대기를 줄이라는 요청이며, 실제 버퍼나 전체 지연이 0 ms라는 의미는 아닙니다. 미지원 또는 설정 실패 시 **저지연 · 버퍼 자동**으로 표시하고 브라우저 기본값을 사용합니다.
- **혼잡 시 전송량 조절**은 기본으로 켜져 있습니다. 시작 후 8초를 기다린 뒤, 최근 네 번의 서로 다른 수신 보고 중 세 번 이상에서 긴 수신 버퍼와 송신 대기·패킷 손실·RTT 증가 등의 혼잡 근거가 함께 관측될 때 전송률 상한을 20%씩 낮춥니다. 최소 6초 간격이며, 안정된 보고가 8번 이어지면 최소 16초 간격으로 10%씩 복원합니다. 실제 전송률을 강제로 높이거나 해상도·목표 프레임·협상 코덱을 바꾸지는 않습니다. 압축 화질은 달라질 수 있습니다.
- 전송률 하한은 선택한 상한의 35%와 실제 캡처 크기·목표 프레임에 따른 보수적 기준 중 큰 값입니다. Full HD / 60 fps / 선명하게에서는 24 → 최저 8.4 Mbps입니다. 이 하한은 화질 보장 수치가 아닌 과도한 감소를 막는 휴리스틱입니다. 수신 버퍼만 높거나 처리 부하·오래된 통계·정지 구간일 때는 낮추지 않습니다. `setParameters()` 이후 실제 상한을 다시 읽어 적용을 확인합니다.
- 같은 장면에서 효과를 비교하려면 전송을 중지하고 **혼잡 시 전송량 조절**만 끈 뒤 다시 시작합니다. H.265·해상도·목표 프레임은 동일하게 두고 버퍼·끊김·실제 전송률을 비교합니다. 기기 브라우저의 버퍼 상한을 직접 강제하거나 지연 감소를 보장하는 기능은 아닙니다.
- Windows의 **왕복**은 네트워크 RTT, 뷰어의 **버퍼**는 최근 구간의 수신 버퍼 평균 대기 시간입니다. 어느 것도 전체 화면 지연을 뜻하지 않습니다. 통계가 없거나 새 프레임이 없으면 수치를 추정하지 않고 —로 표시합니다.
- 비교하려면 전송을 중지한 뒤 저지연 체크를 끄고 다시 시작합니다. 화질·프레임 선택은 유지하고 수신 버퍼를 자동 설정으로 돌립니다. 끊김이 있으면 해상도는 유지한 채 30 fps로 비교할 수 있습니다.
- 이전 저지연 버전은 1280 × 800 / 60 fps로 고정되어 Full HD 원본이 1280 × 720으로 축소되었습니다. 현재 버전은 이 강제 축소를 제거했습니다. 실제 기기의 체감 개선 및 전체 지연 감소량은 별도로 비교해야 합니다.

참고: [WebRTC 수신 버퍼 설정](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpReceiver/jitterBufferTarget), [콘텐츠 및 프레임 유지 우선순위](https://www.w3.org/TR/mst-content-hint/), [WebRTC 수신 통계 정의](https://www.w3.org/TR/webrtc-stats/).

### 지연·PC 사용량 진단

화면을 전송한 뒤 Windows 앱의 **지연·PC 사용량 진단**을 펼칩니다. 약 2초마다 최근 구간을 계산하고, 연결된 기기의 수신 통계도 PC에 표시합니다. **진단 결과 복사**로 설정과 수치를 JSON으로 복사할 수 있습니다. 화면 영상, 접속 토큰, IP 주소와 SDP는 이 보고서에 포함하지 않습니다.

| 항목 | 측정 범위 |
| --- | --- |
| PC 인코딩 | 최근 `totalEncodeTime` 증가량 / 인코딩 프레임 수 증가량 |
| 송신 대기 | RTP 패킷 생성부터 OS 소켓 전달까지의 평균 대기. **패킷당** 값이며 네트워크 편도 지연이 아님 |
| 기기 수신 버퍼 | 최근 프레임이 수신 버퍼에 머문 평균 시간 |
| 기기 디코딩 | 최근 디코딩 프레임당 처리 시간 |
| 첫 패킷 수신 → 디코딩 완료 | 프레임 조립·버퍼·디코딩을 포함하므로 위 항목과 중복됨 |
| 이 Sidepad의 CPU | 현재 인스턴스의 프로세스별 누적 CPU 시간 차이를 전체 논리 코어 용량으로 나눈 비율. 다른 Sidepad 인스턴스와 Windows 합성기 등의 부하는 포함하지 않음 |

이 수치를 더해 전체 지연으로 해석하지 않습니다. 캡처 대기·디스플레이 표시 지연·GPU 사용률은 측정하지 않으며, RTT를 절반으로 나눠 편도 지연으로 간주하지도 않습니다. 첫 구간, 새 프레임이 없는 구간, 통계 미지원은 `—`로 표시합니다. 스트림·코덱 변경 시 계산 기준을 초기화하고, 6.5초 이상 갱신되지 않은 수신 통계는 숨깁니다.

인코더 이름과 코덱은 브라우저의 실제 보고값입니다. `powerEfficientEncoder`는 하드웨어 가속 여부에 대한 참고값이며 그 값만으로 NVENC 사용을 확정하지 않습니다. 브라우저가 이름을 공개하지 않으면 **확인 불가**로 표시합니다. **영상 인코딩 가속 지원**은 Electron 기능 상태이며, 실제 스트림에서 사용하는 인코더와는 구분합니다.

진단은 CPU/대역폭 제한, 긴 송신 대기, 느린 디코딩, 큰 수신 버퍼를 구분하는 참고 안내를 제공합니다. `latencyControl`에는 혼잡 조절 상태·설정한 전송률 상한·하한·조정 횟수가 기록됩니다. `receiver.jitterMs`는 RTP 패킷 도착 변동 추정값이며, `assemblyMs`는 여러 패킷으로 구성된 프레임의 첫 패킷부터 마지막 패킷까지의 조립 시간입니다. 둘 다 전체 지연이 아니며 버퍼 수치와 더하지 않습니다. `bufferApi`는 실제 지원·설정 확인된 API 이름입니다. 영상 프레임 큐는 WebRTC가 관리하며, 앱이 오래된 압축 프레임을 강제로 버리는 기능은 없습니다. 최소 수신 버퍼 요청도 브라우저가 실제 적용 가능한 범위로 제한합니다. 진단 메시지 자체는 소켓이 밀릴 때 버려 통계 때문에 대기열이 커지지 않도록 했습니다.

### 최초 가상 모니터 설정

1. 앱의 **새 가상 모니터 추가 → 드라이버 설치 및 설정**을 누릅니다. 보조 모니터가 없으면 설치 안내가 바로 표시됩니다.
2. 설치 EXE 버전은 포함된 서명 드라이버를 사용합니다. 소스 실행 버전은 드라이버가 없으면 WinGet으로 `VirtualDrivers.Virtual-Display-Driver` 25.7.23을 받습니다. Windows 관리자 확인 후 드라이버를 등록하며, 기존 정상 드라이버는 재등록하지 않습니다.
3. 가상 모니터를 **1920 × 1080 / 60 Hz 확장 화면**으로 자동 설정하고 실제 적용 결과를 확인합니다. 기존 물리 모니터의 주 모니터 지정·해상도·주사율·배치를 유지합니다. 기존 가상 화면 위치는 새 크기에서도 인접하고 겹치지 않으면 유지하고, 그렇지 않으면 기존 화면들의 오른쪽에 붙입니다.
4. 완료 안내 후 가상 디스플레이를 선택하고 전송을 시작합니다. **Windows에서 화면 배치하기**로 원하는 위치로 옮길 수 있습니다.
5. 재부팅이 필요하다고 나오면 Windows를 재시작한 뒤 같은 버튼을 다시 눌러 화면 설정을 마칩니다. WinGet이 없거나 설치에 실패하면 **공식 다운로드**로 드라이버를 설치한 뒤 버튼을 다시 누릅니다. 가상 디스플레이가 여러 개이거나 주 모니터이면 자동 변경하지 않고 안내합니다.

버튼은 드라이버 등록 결과와 화면 설정 결과가 모두 확인돼야 성공으로 표시합니다. 인증서 저장소나 Windows 드라이버 보안 정책은 변경하지 않습니다. 드라이버는 MIT 라이선스로 사용할 수 있으며 재배포 시 고지를 유지해야 합니다. 자세한 내용은 [서드파티 고지](THIRD_PARTY_NOTICES.md)와 [원본 라이선스](licenses/Virtual-Display-Driver.txt)를 참고하세요.

드라이버 설치는 사용자가 해당 버튼 또는 설치 스크립트를 실행했을 때만 진행됩니다. Sidepad 종료 시 가상 모니터는 Windows에 남습니다. 사용하지 않을 때는 Windows 디스플레이 설정에서 해당 디스플레이를 연결 해제하거나 Virtual Driver Control에서 비활성화하세요.

### Wi-Fi로 사용

1. PC와 기기를 같은 공유기 네트워크에 연결합니다. PC는 해당 공유기에 유선 LAN으로 연결해도 됩니다.
2. 앱의 네트워크 주소가 기기에서 접근 가능한 LAN 주소인지 확인합니다. VPN·가상 네트워크 어댑터가 있으면 목록에서 Wi-Fi/LAN 주소를 선택합니다.
3. 기기 카메라로 QR 코드를 스캔하고 브라우저에서 연 뒤 **연결하기**를 누릅니다. 카메라 사용이 어려우면 **연결 링크 복사**로 전체 링크를 전달합니다.
4. Windows 앱에서 **화면 전송 시작**을 누릅니다.
5. PC에서 창을 가상 모니터 방향으로 끌어 옮깁니다. `Win + Shift + 방향키`로 현재 창을 다른 모니터로 옮길 수도 있습니다.
6. 기기에서 전체 화면 및 도구 숨기기를 사용할 수 있습니다. 입력은 PC의 키보드와 마우스를 사용합니다.

새 버전의 기본 설정은 저지연 모드, 최대 1920 × 1200, 목표 60 fps, 전송률 상한 12 Mbps입니다. 현재 1920 × 1080 원본은 해당 해상도로 전송합니다. 두 모드 모두 화질과 프레임을 직접 선택할 수 있습니다. 실제 해상도는 원본 비율과 선택한 최대 크기를 따르며, 프레임과 비트레이트는 GPU, 화면 변화량, Wi-Fi 환경에 따라 달라집니다. Windows 앱의 해상도는 전송 통계가 오기 전에는 캡처 크기, 이후에는 인코더가 보고한 실제 전송 크기를 표시합니다. 5 GHz 또는 6 GHz Wi-Fi에서 먼저 시험해 보세요.

## 연결 문제

- **페이지가 열리지 않음:** PC 앱이 실행 중인지, 주소가 Wi-Fi/LAN 주소인지, 기기들이 같은 공유기인지 확인합니다. 게스트 네트워크·AP 격리·VPN은 연결을 막을 수 있습니다. PC의 네트워크가 바뀌면 앱을 다시 시작합니다.
- **PC에는 연결되지만 영상이 안 나옴:** Windows 방화벽의 앱 허용 여부를 확인합니다. 제어 연결은 TCP 3210(미리보기 3212), WebRTC 영상은 동적 UDP 포트를 사용합니다. 필요한 경우에만 관리자 PowerShell에서 `scripts/allow-firewall.ps1`을 실행합니다. 해당 스크립트는 이 앱 실행 파일에 한해 개인 네트워크·로컬 서브넷에서만 규칙을 추가합니다.
- **보조 화면이 없음:** 가상 모니터가 드라이버에서 활성화되었는지, Windows에서 복제가 아닌 확장으로 설정되었는지 확인합니다. 앱은 기본 화면을 전송 대상으로 제공하지 않습니다.
- **화면이 흐리거나 느림:** 화질과 프레임을 낮추거나 Windows의 가상 모니터 해상도를 조정합니다. 앱이 표시하는 프레임은 정지 화면에서 낮게 나올 수 있습니다.
- **기기 화면 잠금 또는 브라우저 전환 후 끊김:** 브라우저로 돌아와 **다시 연결**합니다. 화면 켜짐 유지 API는 브라우저와 HTTP 환경에 따라 제공되지 않으므로 장시간 사용 시 기기 자동 잠금 설정을 조정해야 할 수 있습니다.
- **링크가 만료됨:** 앱을 재실행하면 연결 토큰이 바뀝니다. 새 QR 코드를 스캔합니다.
- **3210 포트가 사용 중:** PowerShell에서 `$env:SIDEPAD_PORT = '3211'`로 지정한 후 실행합니다. 방화벽 스크립트도 같은 `-Port` 값으로 실행합니다.

방화벽 규칙 제거는 관리자 PowerShell에서 다음과 같이 할 수 있습니다.

```powershell
Get-NetFirewallRule -DisplayName 'Sidepad LAN signaling','Sidepad LAN video' -ErrorAction SilentlyContinue | Remove-NetFirewallRule
```

## 구현 구조

```text
Windows 가상 디스플레이 (외부 IDD 드라이버)
  → Electron desktopCapturer / getDisplayMedia
  → WebRTC 비디오 인코딩 (공통 H.264 / HEVC 규격 협상)
  → 로컬 네트워크 P2P 전송
  → 기기 브라우저 <video playsinline>

Windows 앱 ↔ Node HTTP/WebSocket 서버 ↔ 기기 뷰어
             연결 협상만 전달
```

가상 모니터 드라이버는 Windows가 별도 작업 공간을 만들도록 하고, Sidepad는 그 화면을 영상으로 캡처합니다. Node 서버는 Windows의 Sidepad 프로세스 안에서 실행됩니다. QR 링크로 뷰어 페이지를 받아 인증한 뒤 WebSocket으로 영상 규격과 접속 주소를 교환합니다. 실제 영상은 별도의 WebRTC 연결로 PC와 기기 사이를 직접 이동하며, Node 서버가 영상 프레임을 중계하지 않습니다. 외부 클라우드·STUN·TURN은 사용하지 않습니다.

연결 페이지와 협상은 TCP 3210(미리보기 3212), 영상은 WebRTC가 협상한 동적 포트를 사용합니다. PC가 공유기에 유선으로 연결되고 기기가 Wi-Fi로 연결되어도 같은 LAN에서 동작합니다. 앱의 주소 선택은 QR 링크 주소를 고르며, 영상 전송 어댑터를 강제로 고정하는 기능은 아닙니다. 키보드·마우스 입력은 현재 Windows에서 처리합니다.

화면 지연에는 캡처 대기, 영상 압축, 네트워크 전달, 수신 버퍼, 디코딩과 화면 표시가 모두 포함됩니다. 저지연 설정은 그중 수신 버퍼와 PC의 추가 미리보기 작업을 줄이려는 요청이며, 해상도를 낮추지 않아도 사용할 수 있습니다.

- `src/main.cjs`: Windows 앱, 디스플레이 열거, 선택 화면 캡처 권한, 로컬 서버, 드라이버 설치 버튼.
- `src/preload.cjs`: 제한된 IPC API. 렌더러의 Node.js 접근을 차단합니다.
- `src/server.cjs`: 뷰어 파일 및 인증된 한 기기의 연결 협상. 외부 STUN/TURN을 사용하지 않습니다.
- `src/host/`: Windows 컨트롤 UI, 화면 캡처, WebRTC 송신.
- `src/shared/streaming.js`: 전송 프로필, 브라우저 기능 감지, 최근 수신 버퍼 대기 시간 계산.
- `src/shared/diagnostics.js`: 송수신 구간별 통계, 기기 보고값 검증, 오래된 통계 제거 및 진단 안내.
- `src/shared/codecs.js`: H.264 프로파일 구분, 지원되는 코덱의 우선순위, 실제 인코더 판별 및 협상 진단.
- `src/shared/latency.js`: 수신 통계와 송신 혼잡을 함께 확인하는 제한적 전송률 조절. 오래된 통계·중복 보고·과도한 화질 감소를 방지합니다.
- `src/viewer/`: 브라우저 수신, 재연결, 전체 화면, 수신 통계.
- `scripts/install-driver.ps1`: 공식 WinGet 패키지를 통한 별도 드라이버 설치.
- `scripts/complete-driver-install.ps1`: 이미 설치된 공식 패키지에서 서명을 검증하고 드라이버 장치를 등록합니다. 관리자 PowerShell이 필요하며 인증서 저장소나 보안 정책은 변경하지 않습니다.
- `scripts/configure-virtual-display.ps1`: 가상 디스플레이를 조회합니다. `-Apply`를 지정하면 기존 물리 모니터 설정을 유지하며 오른쪽에 1920 × 1080 / 60 Hz로 확장 배치합니다.
- `scripts/allow-firewall.ps1`: 필요한 경우만 실행하는 로컬 네트워크 방화벽 규칙.

보조 화면 생성은 Windows IDD 계층의 기능이며, 브라우저만으로 새로운 Windows 디스플레이를 만들지는 않습니다. 자체 드라이버 개발로 확장하려면 Microsoft의 [IddCx 개요](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/indirect-display-driver-model-overview)와 [IddSample](https://learn.microsoft.com/en-us/samples/microsoft/windows-driver-samples/indirect-display-driver-sample/)부터 시작할 수 있습니다.

## 현재 범위와 제약

- Windows 앱과 기기용 웹 뷰어를 구현했습니다. 가상 모니터 드라이버는 외부 의존성입니다.
- 영상만 전송하며 기기의 터치·펜 입력, 오디오, HDR, USB 전송은 구현하지 않았습니다.
- WebRTC 미디어는 DTLS-SRTP로 전송되지만, 현재 연결 페이지와 시그널링은 **HTTP/WS**입니다. 연결 링크에 임의의 192비트 토큰을 사용해도 공유 네트워크에서의 도청·변조를 방지하는 HTTPS 인증을 대체하지 못합니다. 현재 버전은 신뢰하는 개인 LAN의 개발용입니다. 배포 버전에는 인증서 신뢰 설정을 갖춘 HTTPS/WSS와 기기 인증이 필요합니다.
- 접속 토큰은 URL의 fragment에 넣어 일반 HTTP 요청·서버 로그에 포함되지 않게 했습니다. 링크를 가진 기기는 한 번에 한 대 연결할 수 있습니다. 소켓 Origin 검사, 최대 메시지 크기, 인증 시간제한, 메시지 종류 제한을 적용했습니다.
- Wi-Fi 지연 시간, 장시간 안정성, 실제 기기 브라우저 호환성은 실기기 테스트 전입니다. 60 fps나 특정 지연 시간을 보장하지 않습니다.
- 실제 실행은 네트워크, 가상 모니터, Windows 방화벽 설정이 완료되어야 합니다. 이 PC의 가상 모니터 설치 및 확장 설정은 완료했습니다. 방화벽 변경은 실행하지 않았습니다.

## 검증

```powershell
npm.cmd run check
npm.cmd test
npm.cmd run smoke
npm.cmd run benchmark
npm.cmd run probe:codecs
```

`test`는 저지연 프로필, 지원되지 않는 브라우저 API의 대체 처리, 표준 모드 복귀, 통계 계산과 정적 파일 노출 범위, 토큰 인증, 동시 연결 제한, Origin 검사, 이전 연결의 메시지 차단, 전송 중지, 잘못된 메시지를 검증합니다. 전송량 조절은 지속/일시 혼잡, 수신 버퍼만 높은 경우, 처리 부하, 중복·오래된 보고, 적용 실패, 화질 보호 하한, 느린 복원도 검증합니다.

`smoke`는 실제 Windows 화면을 캡처하고 숨겨진 Chromium 뷰어에 WebRTC로 보내 프레임이 재생되는지 검증합니다. 저지연 송수신 설정 적용, 표준 모드 복귀, 재협상, 중지·재시작, 뷰어 새로고침도 확인합니다. 별도 사용자 프로필과 자동 할당 포트를 사용하여 실행 중인 앱과 충돌하지 않습니다. 보조 화면이 없을 때만 이 테스트 모드에서 기본 화면을 사용합니다. 캡처한 바탕 화면 영상은 파일로 저장하지 않습니다. 앱 UI와 수신 대기 화면만 `artifacts/`에 저장합니다.

`benchmark`는 전송량 자동 조절을 끄고 같은 최대 1920 × 1200, 목표 60 fps, 상한 12 Mbps로 저지연/표준 모드를 순서대로 비교합니다. 각 모드에서 8초 안정화 후 8개 구간을 수집하고 구간 평균값들의 중앙값을 요약합니다. `artifacts/diagnostics.json`과 `artifacts/benchmark.json`에 수치만 저장합니다. 현재 바탕 화면의 내용은 고정된 벤치마크 영상이 아니며, 동일 PC의 로컬 연결이므로 실제 Wi-Fi/기기 성능이나 전체 화면 지연 측정으로 해석할 수 없습니다. `smoke`와 같은 프로필을 쓰므로 두 명령을 동시에 실행하지 않습니다.

`npm.cmd run benchmark -- --pattern`은 보조 화면 위에 같은 CSS 애니메이션을 잠시 표시해 화면 내용의 차이를 줄입니다. 기존 창은 닫거나 이동하지 않으며, 테스트 창은 성공·실패 모두 자동으로 닫습니다. 결과는 `artifacts/benchmark-pattern.json`에 저장합니다. 이때 CPU 수치는 송신·로컬 수신·테스트 패턴을 포함한 테스트 인스턴스 전체의 값입니다. 배경 작업 부하는 통제하지 않으므로 작은 차이를 성능 개선으로 단정하지 않습니다.

2026-11-18 로컬 비교에서는 실제 인코더가 `MediaFoundationVideoEncodeAccelerator (NVIDIA H.264 Encoder MFT)`로 보고되었습니다. 1920 × 1080 / 목표 60 fps의 같은 패턴에서 아래 값을 얻었습니다. 각 값은 8개 구간 평균의 중앙값이며 전체 화면 지연이 아닙니다.

| 측정 항목 | 최소 버퍼 요청 | 자동 버퍼 |
| --- | ---: | ---: |
| 인코딩 / 프레임 | 7.46 ms | 7.61 ms |
| 수신 버퍼 / 프레임 | 7.01 ms | 7.14 ms |
| 디코딩 / 프레임 | 0.35 ms | 0.37 ms |
| 실제 인코딩 프레임 | 57.08 fps | 57.06 fps |
| 테스트 인스턴스 전체 CPU | 6.16% | 7.14% |

이 결과에서 모드 간 지연 개선은 입증되지 않았습니다. 일반 바탕 화면을 순차 측정했을 때는 화면 내용과 전송량이 달라 수신 버퍼가 크게 달라졌습니다. 이미 하드웨어 인코딩을 사용하는 상태이므로 네이티브 송신 엔진 교체나 임의의 브라우저 내부 플래그 적용은 하지 않았습니다. 실제 기기를 새 미리보기 QR로 연결하고 같은 작업 중 진단을 수집해 판단할 수 있습니다.

### 코덱 선택 재현 검증

수신 버퍼 개선판 검증(2026-11-18): 단위·프로토콜 테스트 28개와 문법 검사를 통과했습니다. 실제 가상 화면을 사용하는 `smoke -- --device-codecs`에서 NVIDIA HEVC, 1920 × 1080, 목표 60 fps를 확인했고, 연결 중 전송률 상한을 낮췄다가 복원해도 코덱·해상도 배율·프레임 상한이 유지됨을 확인했습니다. 로컬 검증은 기능과 재연결 확인이며, 실제 Wi-Fi의 수신 버퍼 감소량을 입증하지는 않습니다.

같은 날 iPad Air 5 / Chrome 연결에서도 영상 재생과 자동 조절을 확인했습니다. 전송률 상한은 24 → 19.2 → 15.3 → 12.2 → 9.7 → 8.4 Mbps로 조절됐으며, 수집한 16개 구간 모두 NVIDIA HEVC와 1920 × 1080을 유지했습니다. 약 30초 동안 실제 송신은 약 57 fps였고 패킷 손실 0, 제외 프레임 2, 멈춤 보고 1회가 관측됐습니다. 변경 전 8개 구간과 변경 후 16개 구간의 수신 버퍼 중앙값은 약 68 ms와 61 ms였지만, 화면 내용·측정 시간·동시 실행 부하가 달라 제어된 성능 비교가 아닙니다. 이 표본만으로 지연 개선을 확정하지 않습니다. 해당 브라우저는 두 수신 버퍼 API를 모두 제공하지 않았으며 수신 버퍼 상한을 강제하는 기능은 추가되지 않았습니다. 원시 진단은 Git에서 제외되는 로컬 `artifacts/buffer-device-validation.json`에만 보관합니다.

`probe:codecs`는 이 PC의 가상 모니터를 같은 해상도와 목표 60 fps로 보내며 수신 프로파일을 하나씩 제한합니다. Electron 45.3.4 / Chromium 156.0.8078.100 / RTX 3060 Ti에서 다음 선택을 재현했습니다. 수신 제한은 브라우저가 실제 지원하는 코덱의 부분집합만 사용합니다.

| 수신 규격 | 실제 선택된 인코더 |
| --- | --- |
| H.264 Baseline `42001f` | NVIDIA H.264 Encoder MFT |
| H.264 Constrained Baseline `42e01f` | OpenH264 |
| H.264 Main `4d001f` | NVIDIA H.264 Encoder MFT |
| H.264 High `640032` | NVIDIA H.264 Encoder MFT |
| HEVC Main | NVIDIA HEVC Encoder MFT |

`npm.cmd run smoke -- --device-codecs`는 수신 코덱을 H.264 Constrained Baseline + HEVC로 제한한 상황에서 새 우선순위가 HEVC를 선택하는지, 실제 NVIDIA 인코더와 1920 × 1080 수신을 확인합니다. 이 재현 테스트는 NVIDIA 및 HEVC 지원이 있는 환경용이며 실기기 검증을 대체하지 않습니다. 프로브 결과는 `artifacts/codec-probe.json`에 저장됩니다. 프로브·smoke·benchmark는 같은 테스트 프로필이므로 동시에 실행하지 않습니다.

실기기 확인(2026-11-18): iPad Air 5 / iPadOS 26 이상 / Chrome은 H.264 `640c1f`(Constrained High), `42e01f`(Constrained Baseline), HEVC 등을 광고했습니다. PC의 H.264 High `640032`와 기기의 Constrained High는 서로 다른 프로파일이므로, 기존 H.264 우선 협상에서는 공통 `42e01f` 경로가 사용될 수 있습니다. 수정 후 실제 기기 응답은 HEVC를 먼저 선택했고, 송신 통계에 `MediaFoundationVideoEncodeAccelerator (NVIDIA HEVC Encoder MFT)`와 `powerEfficientEncoder=true`, 실제 송수신 해상도 1920 × 1080이 확인됐습니다. 사용자가 기기 영상 재생도 확인했습니다.

실기기 샘플에서 인코딩은 약 5.5–5.8 ms, 송신은 약 57 fps였으며 수신 브라우저의 버퍼 제어는 여전히 미지원입니다. 하드웨어 전환 성공과 전체 화면 지연 개선은 별개입니다. 구간별 수치는 화면 내용·전송량·Wi-Fi 상태에 따라 바뀌므로 이전 한 번의 샘플과 비교해 전체 지연 감소를 단정하지 않습니다.

검증 환경: 2026-11-18에 Virtual Display Driver 25.7.23 패키지의 드라이버를 설치하고, 가상 화면 `VDD by MTT`를 주 모니터 오른쪽에 1920 × 1080 / 60 Hz로 확장했습니다. 기존 두 물리 모니터의 배치와 144 Hz, 주 모니터 지정은 유지했습니다. `smoke`는 이 Full HD 화면을 선택했을 때 저지연 모드에서 수신 영상도 1920 × 1080인지 확인하며, 로컬 Chromium 간 재연결·중지·재시작·새로고침을 검증합니다. **별도 기기에서의 실제 Wi-Fi 지연과 장시간 안정성은 자동 테스트 범위에 포함되지 않습니다.**

브랜딩·자동 설정 검증(2026-11-18): 테스트 29개(설치 흐름 10가지 모의 시나리오 포함), JavaScript/PowerShell 문법 검사, 실제 가상 화면의 NVIDIA HEVC / Full HD 전송·재연결 검증을 통과했습니다. 설치 스크립트를 이 PC의 기존 드라이버에 실행해 1920 × 1080 / 60 Hz 확장 설정과 두 물리 모니터의 배치·144 Hz 보존을 확인했습니다. 드라이버가 없는 새 Windows 환경의 최초 설치는 이번 변경에서 별도로 실증하지 않았습니다.

설치 EXE 0.2.0 검증(2026-11-18): 테스트 29개와 설치 흐름 12가지 시나리오를 통과했습니다. 실제 NSIS EXE를 공백이 포함된 별도 경로에 설치하고, Windows 관리자 확인 후 기존 드라이버 재사용·1920 × 1080 / 60 Hz 확장·물리 화면 배치와 144 Hz 보존을 확인했습니다. 설치된 EXE에서도 NVIDIA HEVC Full HD 전송·중지·재시작·재연결을 검증했습니다. 방화벽 규칙은 해당 실행 파일, Private 프로필, LocalSubnet 범위로 확인했습니다. 검증용 앱 제거 후 그 규칙도 제거되고 가상 드라이버는 유지됐습니다. 포함된 드라이버 카탈로그는 SignPath Foundation 유효 서명을 유지합니다. **드라이버가 전혀 없는 새 Windows PC의 최초 등록과 재부팅 후 재개 경로는 아직 실증하지 않았습니다.**

프로젝트는 Electron, ws, qrcode를 사용하며 NSIS 설치 EXE는 electron-builder로 만듭니다. 버전은 `package-lock.json`에 고정되어 있습니다. 사용자 세션·연결 토큰·실행 기록·테스트 화면 캡처는 설치 파일과 Git에서 제외합니다.
