# Sidepad 개발 안내

## 소스에서 실행

Windows 10/11 x64와 Node.js 22.12 이상이 필요합니다. 저장소를 클론한 뒤 루트 폴더에서 실행하세요.

```powershell
npm.cmd ci
npm.cmd start
```

기본 앱은 3210 포트를 사용합니다. 별도로 실행하는 `npm.cmd run preview`는 3212, `preview:hardware`는 3213, `preview:buffer`는 3214 포트와 전용 프로필을 사용합니다. 시험할 창에 표시된 QR 코드로 연결하세요.

## 설치 파일 빌드와 배포

`npm.cmd run dist:win`은 공식 드라이버 ZIP의 SHA-256과 카탈로그 서명을 확인한 뒤 앱과 드라이버를 NSIS 설치 파일로 묶습니다. 결과는 `dist/`에 생성됩니다. [드라이버 배포 고지](../THIRD_PARTY_NOTICES.md)

1. `package.json`과 `package-lock.json`의 버전을 맞춘 뒤 해당 커밋에 `v<버전>` 태그를 붙여 push합니다.
2. **Windows release draft** 워크플로가 Windows에서 테스트와 빌드를 실행합니다. 성공하면 릴리스 초안에 설치 EXE, SHA-256, 한국어 설치 안내가 첨부됩니다.
3. 초안의 EXE를 받아 설치와 기기 연결을 확인한 뒤 **Edit → Publish release**로 공개합니다. 새 버전을 배포하면 [README 다운로드 링크](../README.md)와 버전 표기도 갱신하세요.

기존 태그를 다시 빌드할 때는 **Run workflow**에서 브랜치 `main`을 선택하고 태그명을 입력합니다. [워크플로 보기](../.github/workflows/windows-release.yml)

## 화면 전송 구조

Windows 가상 디스플레이 → Electron 화면 캡처 → WebRTC 인코딩 → 로컬 네트워크 → 기기 브라우저 순서로 영상을 보냅니다.
PC의 HTTP/WebSocket 서버는 뷰어 페이지를 제공하고 접속 토큰으로 기기 한 대를 인증한 뒤 연결을 협상합니다. 영상은 PC와 브라우저 사이의 WebRTC 연결로 전송합니다.

기본 연결 포트는 TCP 3210이고 영상은 WebRTC가 협상한 동적 포트를 사용합니다. 연결 페이지와 시그널링은 HTTP/WS이므로 신뢰하는 개인 LAN에서 사용하세요. 키보드와 마우스 입력은 Windows에서 처리합니다. v0.2.0은 기기의 터치 입력을 PC로 전달하는 기능을 지원하지 않습니다.

## 하드웨어 인코딩 선택

기본 **하드웨어 우선**은 송신·수신 양쪽의 `setCodecPreferences()`를 사용합니다. 실제 브라우저가 지원한다고 광고한 H.264 High/Main/Baseline을 먼저 고려하고, 그 공통 규격이 없으면 지원되는 HEVC(H.265)를 Constrained Baseline보다 우선합니다. 해상도와 프레임 설정은 바꾸지 않습니다. **호환성 우선**을 선택하면 기존처럼 H.264를 먼저 고려합니다.

Windows Chromium의 Media Foundation 인코더는 NVIDIA에서 H.264 **Constrained Baseline**을 제외하는 제한이 있습니다. 이 규격만 우선 협상하면 GPU 가속이 활성화된 PC에서도 OpenH264로 전환될 수 있습니다. H.264를 모두 같은 우선순위로 취급하던 기존 코드를 프로파일별 우선순위로 바꾸고, 수신 측도 동일한 선호도를 적용했습니다. [Chromium 공식 구현](https://chromium.googlesource.com/chromium/src/+/main/media/gpu/windows/media_foundation_video_encode_accelerator_win.cc)

이 기능은 지원되지 않는 프로파일을 SDP에 추가하거나 NVIDIA 드라이버 제한을 해제하지 않습니다. 공통 하드웨어 규격이 없거나 인코더 초기화가 실패하면 호환 가능한 소프트웨어 경로로 연결할 수 있으며, 실제 상태를 표시합니다. **NVIDIA 하드웨어 인코딩 확인**은 `getStats()`의 실제 인코더 이름에 NVIDIA가 보고된 경우에만 표시합니다. 가속 기능의 `enabled` 값만으로 성공을 표시하지 않습니다.

진단 보고서의 `sender.codecParameters`는 선택된 프로파일·패킷화 규격이며, `codecNegotiation`은 송수신 지원 코덱, 선호도 적용 결과, 응답에서 협상한 코덱만 담습니다. 전체 SDP는 포함하지 않습니다.

## 저지연 모드

- 화질·프레임 선택과 저지연 설정을 분리했습니다. 저지연 모드를 켜거나 꺼도 선택한 해상도와 프레임을 바꾸지 않습니다. 기본값은 균형 화질, 목표 60 fps이며, 현재 1920 × 1080 가상 화면을 축소하지 않고 캡처합니다.
- 두 모드 모두 글자 선명도와 해상도 유지를 우선하도록 요청합니다. 네트워크나 인코더가 부족하면 프레임이 줄어들 수 있습니다. 저지연 모드에서는 PC 미리보기 재생을 생략합니다.
- 화질별 전송률 상한은 30 fps에서 가볍게 3 / 균형 8 / 선명하게 16 Mbps, 60 fps에서 각각 4.5 / 12 / 24 Mbps입니다. 상한은 고정 전송률이나 실제 프레임 보장이 아닙니다.
- 수신 브라우저가 지원하면 `jitterBufferTarget = 0`을 요청하고, 이전 API인 `playoutDelayHint`만 제공하면 그 API를 사용합니다. 존재하지 않는 속성을 만들어 성공으로 표시하지 않습니다. 이는 버퍼 대기를 줄이라는 요청이며, 실제 버퍼나 전체 지연이 0 ms라는 의미는 아닙니다. 미지원 또는 설정 실패 시 **저지연 · 버퍼 자동**으로 표시하고 브라우저 기본값을 사용합니다.
- **혼잡 시 전송량 조절**은 기본으로 켜져 있습니다. 시작 후 8초를 기다린 뒤, 최근 네 번의 서로 다른 수신 보고 중 세 번 이상에서 긴 수신 버퍼와 송신 대기·패킷 손실·RTT 증가 등의 혼잡 근거가 함께 관측될 때 전송률 상한을 20%씩 낮춥니다. 최소 6초 간격이며, 안정된 보고가 8번 이어지면 최소 16초 간격으로 10%씩 복원합니다. 실제 전송률을 강제로 높이거나 해상도·목표 프레임·협상 코덱을 바꾸지는 않습니다. 압축 화질은 달라질 수 있습니다.
- 전송률 하한은 선택한 상한의 35%와 실제 캡처 크기·목표 프레임에 따른 보수적 기준 중 큰 값입니다. Full HD / 60 fps / 선명하게에서는 24 → 최저 8.4 Mbps입니다. 이 하한은 화질 보장 수치가 아닌 과도한 감소를 막는 휴리스틱입니다. 수신 버퍼만 높거나 처리 부하·오래된 통계·정지 구간일 때는 낮추지 않습니다. `setParameters()` 이후 실제 상한을 다시 읽어 적용을 확인합니다.
- 같은 장면에서 효과를 비교하려면 전송을 중지하고 **혼잡 시 전송량 조절**만 끈 뒤 다시 시작합니다. H.265·해상도·목표 프레임은 동일하게 두고 버퍼·끊김·실제 전송률을 비교합니다. 기기 브라우저의 버퍼 상한을 직접 강제하거나 지연 감소를 보장하는 기능은 아닙니다.
- Windows의 **왕복**은 네트워크 RTT, 뷰어의 **버퍼**는 최근 구간의 수신 버퍼 평균 대기 시간입니다. 어느 것도 전체 화면 지연을 뜻하지 않습니다. 통계가 없거나 새 프레임이 없으면 수치를 추정하지 않고 —로 표시합니다.
- 비교하려면 전송을 중지한 뒤 저지연 체크를 끄고 다시 시작합니다. 화질·프레임 선택은 유지하고 수신 버퍼를 자동 설정으로 돌립니다. 끊김이 있으면 해상도는 유지한 채 30 fps로 비교할 수 있습니다.
- 이전 저지연 버전은 1280 × 800 / 60 fps로 고정되어 Full HD 원본이 1280 × 720으로 축소되었습니다. 현재 버전은 이 강제 축소를 제거했습니다. 실제 기기의 체감 개선 및 전체 지연 감소량은 별도로 비교해야 합니다.

참고: [WebRTC 수신 버퍼 설정](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpReceiver/jitterBufferTarget), [콘텐츠 및 프레임 유지 우선순위](https://www.w3.org/TR/mst-content-hint/), [WebRTC 수신 통계 정의](https://www.w3.org/TR/webrtc-stats/).

## 지연·PC 사용량 진단

화면을 전송한 뒤 Windows 앱의 **지연·PC 사용량 진단**을 펼칩니다. 약 2초마다 최근 구간을 계산하고, 연결된 기기의 수신 통계도 PC에 표시합니다. **진단 결과 복사**로 설정과 수치를 JSON으로 복사할 수 있습니다. 화면 영상, 접속 토큰, IP 주소와 SDP는 이 보고서에 포함하지 않습니다.

| 항목 | 측정 범위 |
| --- | --- |
| PC 인코딩 | 최근 `totalEncodeTime` 증가량 / 인코딩 프레임 수 증가량 |
| 송신 대기 | RTP 패킷 생성부터 OS 소켓 전달까지의 평균 대기. **패킷당** 값이며 네트워크 편도 지연이 아님 |
| 기기 수신 버퍼 | 최근 프레임이 수신 버퍼에 머문 평균 시간 |
| 기기 디코딩 | 최근 디코딩 프레임당 처리 시간 |
| 첫 패킷 수신 → 디코딩 완료 | 프레임 조립·버퍼·디코딩을 포함하므로 위 항목과 중복됨 |
| 이 Sidepad의 CPU | 현재 인스턴스의 프로세스별 누적 CPU 시간 차이를 전체 논리 코어 용량으로 나눈 비율. 다른 Sidepad 인스턴스와 Windows 합성기 등의 부하는 포함하지 않음 |

이 수치를 더해 전체 지연으로 해석하지 않습니다. 캡처 대기·디스플레이 표시 지연·GPU 사용률은 측정하지 않으며, RTT를 절반으로 나눠 편도 지연으로 간주하지도 않습니다. 첫 구간, 새 프레임이 없는 구간, 통계 미지원은 `—`로 표시합니다. 스트림·코덱 변경 시 계산 기준을 초기화하고, 6.5초 이상 갱신되지 않은 수신 통계는 숨깁니다.

인코더 이름과 코덱은 브라우저의 실제 보고값입니다. `powerEfficientEncoder`는 하드웨어 가속 여부에 대한 참고값이며 그 값만으로 NVENC 사용을 확정하지 않습니다. 브라우저가 이름을 공개하지 않으면 **확인 불가**로 표시합니다. **영상 인코딩 가속 지원**은 Electron 기능 상태이며, 실제 스트림에서 사용하는 인코더와는 구분합니다.

진단은 CPU/대역폭 제한, 긴 송신 대기, 느린 디코딩, 큰 수신 버퍼를 구분하는 참고 안내를 제공합니다. `latencyControl`에는 혼잡 조절 상태·설정한 전송률 상한·하한·조정 횟수가 기록됩니다. `receiver.jitterMs`는 RTP 패킷 도착 변동 추정값이며, `assemblyMs`는 여러 패킷으로 구성된 프레임의 첫 패킷부터 마지막 패킷까지의 조립 시간입니다. 둘 다 전체 지연이 아니며 버퍼 수치와 더하지 않습니다. `bufferApi`는 실제 지원·설정 확인된 API 이름입니다. 영상 프레임 큐는 WebRTC가 관리하며, 앱이 오래된 압축 프레임을 강제로 버리는 기능은 없습니다. 최소 수신 버퍼 요청도 브라우저가 실제 적용 가능한 범위로 제한합니다. 진단 메시지 자체는 소켓이 밀릴 때 버려 통계 때문에 대기열이 커지지 않도록 했습니다.
